# VFP Web 方案

## 1. 结论

针对“VFP系统要上手机、要做真正B/S”的目标，推荐采用下面的主方案：

`IIS + VFP Web 后端 + SQL Server + H5 前端`

其中：

- `VFP` 负责业务规则、权限、报表、数据加工、接口输出。
- `IIS` 负责 HTTP/HTTPS 接入、反向代理、站点管理、证书。
- `SQL Server` 负责正式业务数据存储。
- `H5` 负责手机浏览器页面渲染。

这套方案里，`VFP` 不去冒充浏览器，而是作为真正的服务端程序，通过 HTTP 输出 `HTML` 或 `JSON`。浏览器负责渲染，手机端访问的是标准 Web 页面。

## 2. 方案判断

### 2.1 什么可行

`VFP` 可以在服务器端完成下面这些事：

- 接收 Web 请求
- 调用业务逻辑
- 访问 `DBF` 或 `SQL Server`
- 生成 `HTML`
- 输出 `JSON`
- 管理会话、权限、日志

### 2.2 什么不可行

`VFP` 不能替代手机浏览器本身，也不适合直接承担现代前端交互层。因此不要把目标定成“VFP 单独完成全部 Web 技术栈”，而应该定成：

`VFP 实现后端核心，浏览器使用标准 HTML/CSS/JavaScript`

这才是技术上可落地、成本上可控的方案。

## 3. 两条路线

### 3.1 主方案：新建 Web 模块

适用场景：

- 要做新网页、新手机端
- 接受把前端改成标准 `H5`
- 后端业务仍坚持使用 `VFP`
- 希望接口清晰，便于以后逐步演进

推荐组合：

- Web 服务器：`IIS`
- VFP Web 框架：`West Wind Web Connection`
- 数据库：`SQL Server`
- 前端：`Bootstrap` 或其他响应式 H5

优点：

- 架构清晰，是真正的 `B/S`
- 手机浏览器适配容易做
- 前后端职责明确
- 以后即便替换前端，也不用推翻 `VFP` 业务层

缺点：

- 需要补一层 H5 前端
- 原有 `SCX/VCX` 窗体不能直接拿来当网页

### 3.2 备选方案：现有桌面系统快速浏览器化

适用场景：

- 现有 `VFP` 桌面系统很大
- 想尽量保留原有窗体、事件、代码
- 目标是先跑起来，再逐步整理

推荐组合：

- Web 服务器：`IIS`
- 适配平台：`FoxInCloud`
- 业务层：现有 `VFP` 工程

优点：

- 代码复用率高
- 适合老系统快速 Web 化

缺点：

- 页面结构会更受原桌面程序约束
- 长期看不如 API 化方案清晰
- 对框架和适配工具依赖更高

## 4. 推荐选型

如果你们是“重新做一个 Web 方案”，建议直接选主方案：

`VFP(Web Connection) + SQL Server + H5`

如果你们是“把一个很大的现成桌面系统尽快搬到浏览器里”，才优先考虑：

`VFP(FoxInCloud)`

一句话判断：

- 新项目，选 `Web Connection`
- 老项目快速网页化，选 `FoxInCloud`

## 5. 主方案总体架构

```text
手机浏览器 / 电脑浏览器
        |
     HTTPS
        |
       IIS
        |
 VFP Web 应用(Web Connection)
        |
 业务服务类 / 权限 / 日志 / 报表
        |
    SQL Server
```

## 6. 模块拆分

### 6.1 前端模块

- 登录页
- 首页仪表盘
- 查询列表页
- 单据编辑页
- 报表查看页
- 用户中心

前端只负责：

- 页面展示
- 表单提交
- 调用 API
- 手机适配

### 6.2 VFP 后端模块

- `AuthService`：登录、注销、权限
- `UserService`：用户、角色、菜单
- `OrderService`：单据查询、新增、修改、删除
- `ReportService`：报表输出、Excel/PDF 导出
- `LogService`：操作日志、异常日志

### 6.3 数据模块

- 基础主数据
- 业务单据表
- 权限表
- 日志表
- 接口状态表

## 7. 接口风格

建议采用：

- 页面：`HTML`
- 数据接口：`JSON REST`

接口示例：

- `POST /api/login`
- `GET /api/orders?status=open`
- `POST /api/orders`
- `PUT /api/orders/{id}`
- `GET /api/reports/sales-daily`

这样做的好处是：

- 页面与业务接口分离
- 手机端和电脑端可以复用同一套接口
- 以后如果要做小程序或 App，也能继续复用

## 8. 数据策略

建议分两步：

### 8.1 过渡期

- 老数据仍在 `DBF`
- Web 新模块读写 `SQL Server`
- 由 `VFP` 负责同步或迁移

### 8.2 稳定期

- 正式业务统一落 `SQL Server`
- `DBF` 只保留历史数据或过渡用途

原因很简单：Web 并发、日志、安全、备份、权限控制，都更适合 `SQL Server`。

## 9. 登录与安全

建议标准化处理：

- 全站 `HTTPS`
- 统一登录
- 会话超时控制
- 菜单和按钮级权限
- 关键操作日志
- 导出、删除、审核等敏感动作二次确认

若为内网系统，可先用 `Session/Cookie`；若未来要开放多端接入，可再升级为 `Token` 模式。

## 10. 手机适配原则

- 页面宽度自适应
- 列表优先卡片化
- 查询条件折叠
- 按钮减少并合并动作
- 大表格改成“筛选 + 明细查看”
- 报表优先做摘要页，明细按需展开

不要照搬桌面窗体布局。桌面界面挪到手机上，通常可用性会很差。

## 11. 开发步骤

### 第一步：先打穿最小闭环

先做 3 个页面：

- 登录
- 单据列表
- 单据编辑

先做 5 个接口：

- 登录
- 当前用户信息
- 列表查询
- 单据保存
- 操作日志写入

先打通下面的完整链路：

`浏览器 -> IIS -> VFP -> SQL Server -> VFP -> JSON -> 浏览器`

### 第二步：补权限与日志

- 用户角色
- 菜单权限
- 按钮权限
- 审计日志
- 异常日志

### 第三步：补报表与导出

- 查询统计
- Excel 导出
- PDF 输出

### 第四步：逐步替换老功能

- 每次替换一个业务模块
- 新旧系统并行运行
- 先替换高频查询和轻录入模块

## 12. 部署建议

服务器建议：

- Windows Server
- `IIS`
- `SQL Server`
- 独立应用目录
- 独立日志目录
- 定时备份

部署注意点：

- `VFP 9` 是老技术，生产环境必须固定运行时版本
- 若采用 32 位组件或相关宿主模式，`IIS` 应用池按 32 位方式配置更稳妥
- 所有上传、导出、日志目录单独授权
- Web 与数据库尽量放内网

## 13. 风险与边界

### 13.1 必须接受的现实

- `Visual FoxPro 9.0` 官方支持已于 `2015-01-13` 结束
- 新系统继续使用 `VFP`，本质是“延长既有资产寿命”，不是面向未来十年的理想终局技术栈

### 13.2 仍然适合使用 VFP 的场景

- 团队核心能力在 `VFP`
- 原业务规则大量沉淀在 `VFP`
- 需要低成本、低风险上线 Web 版本
- 系统主要是企业内网或垂直行业场景

### 13.3 不适合继续硬上 VFP 的场景

- 高并发公网业务
- 大规模开放平台
- 重前端交互
- 复杂微服务生态

## 14. 推荐实施策略

建议按下面的顺序推进：

1. 确定主方案采用 `Web Connection`
2. 先做一个手机可访问的最小模块
3. 数据统一落 `SQL Server`
4. VFP 只做业务和接口，不再做新桌面窗体
5. 新功能全部按 `API + H5` 方式开发

这是最稳的走法：既保留 `VFP` 优势，又避免继续把桌面思维硬搬到手机上。
